# Account Recovery 20261013

## Problem

An in-place update from build20 to build22 can retain a version1 local account binding that the current version2 decoder rejects. The native identity service reads that binding before querying OAuth, trapping the user in an account failure page even after Retry. Native exceptions are lost. Graph data must remain owned by its existing account.

## Proposal

Reject unsupported or corrupt bindings without migrating their contents. Classify permanent format rejection separately from inaccessible secure storage and remote failures. Query the independently verified OAuth identity even when a binding is invalid. Rebuild only the advisory binding from that identity, using the current encoder and an atomic Keychain update; never clear graph, outbox, draft, asset or encryption-key data.

JournalPlatformServices owns recovery policy and sanitized stage/type diagnostics. JournalLocalAccountBindingStore owns bounded decoding and Keychain status classification. The existing authentication presentation owner fences cancellation and duplicate actions; a successful browser flow completes account preparation before declaring success. Native host UI retains an accessible sign-in/retry entry after sheet cancellation or failure. OCaml continues to own graph/account isolation and graph selection.

The existing graph UI clears private in-memory drafts when a different account is published. Recovery therefore fences a different verified identity once a graph session has been presented; it retains the advisory binding and refuses to release a foreign account's token to that graph. The UI asks the user to reconnect the original account and finish pending work before changing accounts. Canceling sign-in cannot remove this session fence. Fresh startup can establish a different verified identity without a presented graph or editor drafts; persisted graph/outbox data remains scoped to its original account.

Tests use existing public native requests and authentication actions. The OCaml pure reducer cannot originate this native codec failure: feeding it Account_error would inject an already failed external result. Native services with real binding codecs and isolated storage/auth capabilities are the narrowest reproducing boundary. Simulator acceptance uses a separate synthetic bundle and production views, never real credentials or personal graphs. No Dune or spec changes.

## Decision

Implement the native recovery policy and production recovery/sign-in views. Reject retained version1/corrupt records, independently verify the OAuth identity, and atomically rebuild current-format advisory binding only when storage is accessible. Preserve presented graph identity across cancel, missing SDK session and failed preparation; refuse a different identity/token before publishing an account boundary.

## Alternatives considered

### Migrate or delete retained data

Rejected by the user's explicit no-compatibility policy and requirement to preserve all graph and unsynced data. A verified identity can establish a new advisory binding without interpreting the rejected record.

### Treat all native failures as absent account

This would silently overwrite inaccessible storage or clear an offline identity on a network failure. Temporary failures instead retain the record and offer retry.

## Consequences

- A further cold-start review finding was dynamically reproduced with separate processes and file-backed synthetic Security I/O: failed undo followed by exit exposed unaccepted B on restart. Both original-record and original-absence cold scenarios now fail closed while restoration is unavailable and restore before lookup after recovery.
- A protected companion Keychain journal stores exact prior bytes/absence and the proposed replacement before canonical mutation, with no new access entitlement. Cold access recovers this journal before returning metadata; undecodable journals or failed recovery never fall back to reading the unaccepted canonical value.
- Acceptance is cached only for cleanup, which is attempted promptly off the UI actor. If exit occurs before cleanup, cold access conservatively undoes the advisory binding even if the preceding process had accepted it; a verified session can reestablish it. This preserves data and may require another account preparation. No old-binding migration or graph/outbox reassignment occurs.

- Independent review P1/P2 were dynamically reproduced through public services with delayed saves. A graph presented during save rejected neither identity nor persisted binding; a retired save also cleared a newer error.
- Save now returns an isolated proposal. After the await, the owner rechecks generation and graph account before accepting, clearing diagnostics or publishing identity. Rejection restores the exact prior opaque bytes without migrating them.
- Native access serializes reads, writes and explicit cleanup across the whole proposal. A failed undo retains its snapshot and fails closed; the next access must repair before exposing account metadata. Undo of an initially absent record removes only this proposal's newly created item.
- Native factory tests cover failed undo, reads from another store, successful repair, rejection of a newly created item, and an older undo preceding a newer accepted write. These use synthetic Security I/O and the real native factory/access implementation.

- Native services, recovery and threading tests pass; authentication tests cover preparation failure, duplicate action, cancel, retired completion and sanitized instructions. Synthetic signed Cognito tests pass.
- All production Swift sources typecheck for iPhoneOS using the existing LUI module, without copying or rebuilding the product cache. The existing presentation-anchor deprecation warning remains.
- Independent Simulator probe verifies recovery entry, close/return, success, network failure, in-flight cancel and binding-write failure using production views/services/codecs with synthetic capabilities.
- No graph/outbox/draft/asset/key cleanup, Dune/spec edit, phone installation, real credentials or PR publication. Other rejected graph persistence formats retain their existing error paths.
- Real Cognito and full personal-graph startup remain acceptance work requiring user handoff. A cached OCaml test binary had mismatched source artifacts and is not accepted as current-source validation evidence.

## Acceptance criteria

- Legacy/corrupt bindings never block a verified identity query and can be rebuilt in current format.
- Missing/invalid sessions provide sign-in; canceled or failed sign-in leaves a usable recovery entry.
- Network/Keychain failures retain storage, report only sanitized stage/type/version and can retry.
- Duplicate actions and stale completions cannot publish a retired identity.
- Different identity/token cannot take over a presented graph, including after canceled preparation; reconnecting the original identity remains possible.
- Existing account scope and graph data remain intact when verified identity differs.
- Native tests demonstrate RED then GREEN; synthetic Simulator screens demonstrate entry, success, cancellation and retry.

## Risks

- Rebuilding the advisory binding does not make other rejected catalog/outbox formats compatible. Subsequent graph errors retain their existing recovery paths; no graph reset is introduced.
- Real Cognito and personal graph acceptance require secure user handoff. Synthetic acceptance cannot prove configured production OAuth.
- A save already executing in the serialized native queue may finish after cancellation; completion and graph publication must be fenced, and no unverified identity may be persisted.

## Questions

- No open design question: the user authorized rejection of old formats, a complete in-app recovery flow and preservation of graph data. Phone installation and PR publication remain outside scope.
