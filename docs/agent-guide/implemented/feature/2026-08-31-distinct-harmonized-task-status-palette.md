# Distinct Harmonized Task Status Palette

## Problem

The implemented quick task-status palette documented in
`docs/agent-guide/implemented/feature/2026-08-31-harmonized-task-status-colors.md`
made the four swipe actions theme-aware and gave Light and Dark appearances explicit
foreground/background pairs.
That decision fixed the original contrast and theme-integration problems, but its `No status`
and `Todo` colors remain two closely related blue-grays:

| Quick status | Implemented Light background | Implemented Dark background |
| --- | --- | --- |
| No status | `#455A60` | `#99AFB6` |
| Todo | `#566E7F` | `#B1CADE` |
| Doing | `#00677C` | `#86D1E9` |
| Done | `#006B5E` | `#83D5C5` |

The relationship is harmonious, but it weakens categorical scanning when all four actions
are visible side by side and when the Todo color appears as a narrow timeline rail.
The four states need to feel like members of the same `#00262F`-seeded Material theme while
remaining recognizably different at a glance.

This decision is a follow-up to the implemented decision rather than a rewrite of its
history.
It selects one exact replacement palette while preserving the established token structure,
status semantics, and interaction behavior.

## Proposal

Replace the implemented custom colors with four theme-aware semantic roles whose hues carry
more of the categorical distinction:

- `No status` is a neutral charcoal with a restrained cyan bias.
- `Todo` uses the generated Material tertiary family, a muted indigo that separates planned
  work from both the neutral unset state and the cyan active state.
- `Doing` continues to use the generated Material primary family and therefore remains the
  state most directly tied to the application brand.
- `Done` uses a cyan-harmonized green that reads as completed without becoming a saturated,
  generic success green.

### Candidate palette

| Quick status | Semantic role | Light background | Light foreground | Dark background | Dark foreground |
| --- | --- | --- | --- | --- | --- |
| No status | Unset, neutral | `#4B5E63` | `#FFFFFF` | `#A7B8BC` | `#1B3035` |
| Todo | Planned, inactive | `#585C7E` | `#FFFFFF` | `#C0C4EB` | `#2A2E50` |
| Doing | Active, brand-owned | `#00677C` | `#FFFFFF` | `#86D1E9` | `#003642` |
| Done | Completed, positive | `#006B57` | `#FFFFFF` | `#83D6BD` | `#00382B` |

The Light and Dark `Todo` backgrounds are the current Material tertiary roles generated by
`ColorScheme.fromSeed` from `#00262F` with the pinned `tonalSpot` variant.
The `Doing` backgrounds are the corresponding primary roles.
The custom neutral and completion colors stay close to the same cyan-centered hue system,
but do not collapse into the primary or tertiary families.

The candidate changes three roles relative to the implemented palette and deliberately keeps
`Doing` unchanged:

| Quick status | Intended visible change |
| --- | --- |
| No status | Moves toward a more neutral charcoal and away from Todo's hue |
| Todo | Moves from blue-gray to muted indigo for the largest categorical separation |
| Doing | Retains the theme-primary cyan as the active-state anchor |
| Done | Moves slightly greener to separate completion from active cyan |

### Contrast

The calculated WCAG contrast ratios are:

| Quick status | Light foreground/background | Light background/`#F5FAFD` surface | Dark foreground/background | Dark background/`#0F1416` surface |
| --- | ---: | ---: | ---: | ---: |
| No status | `6.82:1` | `6.48:1` | `6.72:1` | `9.03:1` |
| Todo | `6.47:1` | `6.15:1` | `7.69:1` | `10.90:1` |
| Doing | `6.50:1` | `6.18:1` | `7.66:1` | `10.88:1` |
| Done | `6.48:1` | `6.16:1` | `7.70:1` | `10.88:1` |

Every foreground/background pair exceeds the WCAG AA `4.5:1` threshold for ordinary text.
Every status background exceeds `3:1` against its corresponding surface, preserving non-text
contrast when Todo, Doing, or Done is rendered as a narrow row rail.
Labels, icons, accessibility semantics, and current-state enablement remain the primary cues;
color supplements rather than replaces them.

### Token behavior

The palette remains exactly two brightness-specific sets of explicit background/foreground
pairs.
High Contrast reuses the corresponding normal Light or Dark pair, matching the implemented
decision and avoiding two additional custom palettes.

Todo, Doing, and Done continue to share their semantic background between the full-bleed
quick action and the timeline row rail.
`No status` continues to use its neutral pair only in the quick action and does not gain a
row rail.
The full-bleed action consumes both the background and foreground roles; it does not infer a
foreground from an arbitrary background or assume universal white content.

### Scope boundaries

This exploration changes only the candidate color values for `No status`, `Todo`, `Doing`,
and `Done`.
It does not change:

- action order, labels, icons, geometry, centering, enablement, or accessibility semantics;
- task-status mutation behavior, action IDs, or the `Journal_model.task_state` model;
- category mapping for non-quick statuses or the existing `Later` rail color;
- the absence of a `No status` row rail;
- the Delete action's destructive palette;
- the application theme seed, Material variant, or generated theme roles;
- any file under `spec/`, any Dune file, or any OCaml file in `bonsai_flutter`; or
- the UI limit of at most three dividers.

## Decision

Use the exact Light and Dark semantic pairs in the candidate palette without another hue
iteration.
Replace the implemented palette values while retaining its brightness selection, High
Contrast reuse, rail sharing, and explicit foreground behavior.
The user accepted this palette on 2026-08-31 after reviewing the four colors together.

## Alternatives considered

### Keep the implemented palette

The implemented colors already pass the required contrast thresholds and integrate with
Light and Dark appearances.
Keeping them avoids visual regression updates, but preserves the weak hue separation between
`No status` and `Todo` that prompted this exploration.

### Use a warm Todo color

Amber or orange would make Todo maximally distinct from the other three cyan-centered roles.
It was not selected because warm hues conventionally imply warning, urgency, or attention;
ordinary planned work should not compete with destructive and exceptional states.

### Use built-in Material roles for every status

Mapping all four statuses directly to Material scheme roles would minimize custom values.
Material has no standard completion or success role, however, and using tertiary for Done
would leave Todo without the muted indigo distinction that is central to this exploration.

### Increase saturation across all four roles

More saturated swatches would increase local separation, but four adjacent full-bleed actions
would dominate the restrained cyan theme.
The candidate instead relies on controlled hue differences and strong tone contrast.

## Acceptance criteria

- The exact Light and Dark values in the candidate palette are used as explicit semantic
  background/foreground pairs for all four quick statuses.
- The four adjacent actions are visibly distinguishable in both Light and Dark appearances,
  with Todo reading as muted indigo rather than neutral blue-gray.
- Every label and icon retains at least `4.5:1` contrast against its action background.
- Every Todo, Doing, and Done rail background retains at least `3:1` contrast against the
  corresponding theme surface.
- Doing remains tied to the generated primary family, and Todo remains tied to the generated
  tertiary family.
- Done remains visibly distinct from Doing without becoming a high-chroma generic green.
- `No status` remains neutral, has no row rail, and is distinct from Todo without relying on
  a tone-only difference.
- High Contrast reuses the matching normal Light or Dark status pairs.
- Runtime goldens and macOS validation cover Light, Dark, Light High Contrast, and Dark High
  Contrast without changing established layout or interaction behavior.
- Screenshot evidence shows the four quick actions together in at least Light and Dark macOS
  appearances.
- No model, mutation, layout, `spec/`, Dune, or `bonsai_flutter` behavior changes as part of
  the palette replacement.

## Risks

- The muted indigo Todo role is intentionally less semantically conventional than a neutral
  pending state, so labels and icons must continue to carry the literal meaning.
- Applying Todo, Doing, and Done colors to shared rail tokens changes persistent timeline
  color as well as the transient swipe pane.
- The new Todo hue will produce broad golden-image color differences even when geometry is
  unchanged; implementation review must distinguish expected color pixels from layout drift.
- Reusing normal pairs in High Contrast gives up status-specific contrast escalation, though
  all candidate pairs already exceed the required thresholds.
- Exact fixed exceptions remain coupled to the current `#00262F` seed and `tonalSpot` theme;
  a future seed change would require this palette to be reevaluated.

## Consequences

- Light appearance uses the darker `No status`, Todo, Doing, and Done backgrounds with white
  icon-and-label foregrounds.
- Dark appearance uses the lighter status backgrounds with their explicit dark foregrounds.
- Todo now reads as muted indigo rather than another neutral blue-gray, giving it a visible
  hue distinction from `No status` and Doing.
- Doing remains the theme-primary cyan anchor, while Done moves slightly greener to preserve
  a clear active/completed distinction.
- Todo, Doing, and Done timeline rails continue to use the same brightness-specific
  backgrounds as their quick actions.
- `No status` remains rail-free, `Later` retains its existing rail color, and all status
  actions retain their labels, icons, semantics, ordering, and mutation behavior.
- High Contrast continues to reuse the corresponding normal Light or Dark semantic pairs.
- Exact OCaml and Flutter runtime expectations protect both palettes and their contrast
  requirements, while the affected golden records only the intended rail color changes.
