# Harmonized Quick Task Status Colors

## Problem

The timeline's logical-start swipe pane exposes four quick task-status actions:

```text
No status | Todo | Doing | Done
```

The actions use full-bleed backgrounds and white icon-and-label foregrounds. The current
colors are application-owned fixed RGB values:

| Quick status | Current background |
| --- | --- |
| No status | `#475569` |
| Todo | `#64748B` |
| Doing | `#2563EB` |
| Done | `#058E46` |

These values were selected independently from the application theme. The application theme
is generated by Material `ColorScheme.fromSeed` from the deep cyan seed `#00262F` using the
default `tonalSpot` variant. With the currently pinned Material Color Utilities algorithm,
the normal-contrast schemes include these roles:

| Theme | Surface | Primary | Secondary | Tertiary | On surface |
| --- | --- | --- | --- | --- | --- |
| Light | `#F5FAFD` | `#00677C` | `#4B6269` | `#585C7E` | `#171C1E` |
| Dark | `#0F1416` | `#86D1E9` | `#B2CAD3` | `#C0C4EB` | `#DEE3E6` |

The fixed status palette does not follow this theme's hue, chroma, or light/dark tone
relationships. `Doing` is a high-chroma electric blue beside a restrained cyan theme, and
the current `Done` background has only approximately `4.23:1` contrast against its fixed
white foreground. That is below the WCAG AA `4.5:1` threshold for ordinary text. Reusing
the same mid-tone background in Dark theme also gives up Material's light-background and
dark-foreground pairing.

The row rail and swipe action currently share the Todo, Doing, and Done category colors.
`No status` intentionally has no row rail and receives a neutral color only when it must be
rendered as a full-bleed swipe action.

This proposal is deliberately limited to the four quick statuses above. It does not
design colors for `In review`, `Now`, `Canceled`, `Backlog`, `Waiting`, or `Later`, and it
does not change their model values or existing category mapping.

## Proposal

Replace the four fixed RGB backgrounds with theme-aware semantic status color pairs. Treat
each pair as a custom Material color role rather than as an isolated swatch:

```text
status background + on-status foreground
```

Generate the palette in HCT color space and harmonize each semantic hue toward the theme
seed `#00262F`. Keep chroma restrained so the transient full-bleed swipe pane belongs to the
same visual system as the cyan theme instead of competing with it. Use darker tones in Light
theme and lighter tones with dark foregrounds in Dark theme.

### Recommended normal-contrast palette

| Quick status | Semantic role | Light background | Light foreground | Dark background | Dark foreground |
| --- | --- | --- | --- | --- | --- |
| No status | Unset, neutral | `#455A60` | `#FFFFFF` | `#99AFB6` | `#1F3339` |
| Todo | Planned, inactive | `#566E7F` | `#FFFFFF` | `#B1CADE` | `#1A3343` |
| Doing | Active, theme-owned | `#00677C` | `#FFFFFF` | `#86D1E9` | `#003642` |
| Done | Completed, positive | `#006B5E` | `#FFFFFF` | `#83D5C5` | `#003730` |

`Doing` uses the generated Material primary roles directly because it is the active state
and should have the strongest relationship to the application brand. `Done` moves from a
generic success green toward a cyan-harmonized green. `Todo` is a lower-chroma blue-gray,
while `No status` is darker in Light theme and one tone step lower than Todo in Dark theme
so the two adjacent neutral actions remain distinguishable.

The calculated contrast ratios are:

| Quick status | Light foreground/background | Light background/surface | Dark foreground/background | Dark background/surface |
| --- | ---: | ---: | ---: | ---: |
| No status | `7.28:1` | `6.93:1` | `5.76:1` | `8.09:1` |
| Todo | `5.34:1` | `5.08:1` | `7.74:1` | `10.93:1` |
| Doing | `6.50:1` | `6.18:1` | `7.66:1` | `10.88:1` |
| Done | `6.43:1` | `6.12:1` | `7.73:1` | `10.86:1` |

Every proposed foreground pair exceeds the WCAG AA `4.5:1` ordinary-text threshold. Every
background exceeds the `3:1` non-text contrast threshold against its corresponding theme
surface, so the same semantic color can remain legible when rendered as a narrow row rail.
Color remains supplemental: each action retains its visible label, distinct icon, semantics,
and current-state enablement.

### Theme and token shape

The current `Journal_visual_tokens.resolve` call site already has access to the framework
environment's `brightness` and `high_contrast` values at the application composition point,
although only `high_contrast` is currently passed into token resolution. Implementation can
therefore make brightness explicit without modifying `bonsai_flutter`.

The intended token result for each quick status is a foreground/background pair, selected
by brightness and contrast presentation. The implementation should not infer a foreground
from an arbitrary background and should not retain white as a universal status foreground.
The status rail consumes only the background role. The full-bleed swipe action consumes both
roles.

High Contrast appearances reuse the corresponding normal Light or Dark status pair. They do
not receive separately generated HCT tones. This intentionally keeps the custom status
palette to two brightness variants while the generated Material scheme continues to own the
rest of the application's High Contrast presentation.

### Resolved product decisions

- Todo, Doing, and Done continue to share their semantic backgrounds between swipe actions
  and row rails.
- Dark theme uses the proposed lighter status backgrounds with their explicit dark
  foregrounds.
- High Contrast reuses the corresponding normal Light or Dark status pairs instead of
  generating separate HCT tones.
- `No status` remains absent from row rails and uses its neutral pair only in the full-bleed
  swipe action.

## Decision

Resolve the four quick task statuses from exactly two custom semantic palettes selected by
the framework environment brightness.
Light uses the accepted dark backgrounds with white foregrounds, while Dark uses the
accepted light backgrounds with explicit dark foregrounds.
High Contrast reuses the palette selected by brightness and does not introduce additional
custom status tones.

Keep the custom pairs in `Journal_visual_tokens.Color_exceptions` and pass the current
framework brightness into `Journal_visual_tokens.resolve` at the application composition
point.
Todo, Doing, and Done share their resolved backgrounds with the corresponding row rails.
No status remains rail-free, and Later retains its existing rail color.
The full-bleed swipe action consumes both roles from the resolved pair without inferring a
foreground or sharing the Delete foreground.

### Scope boundaries

The decision changes only the presentation tokens consumed by the four quick status actions
and the shared Todo, Doing, and Done row rails. It does not change:

- quick action order, labels, icons, full-bleed geometry, or centering;
- task-status mutation behavior, action IDs, enablement, or accessibility semantics;
- the exact ten-value `Journal_model.task_state` model;
- category mapping for non-quick exact statuses;
- the existing `Later` category color;
- the absence of a row rail for `No status`;
- the Delete action's destructive palette;
- the application theme seed or Material `tonalSpot` variant;
- any file under `spec/`, any Dune file, or any OCaml file in `bonsai_flutter`; or
- the UI limit of at most three dividers.

## Alternatives considered

### Slightly desaturate the current fixed colors

Keep one palette for both Light and Dark themes, reduce the chroma of the current blue and
green, and retain white foreground content everywhere.

This is simpler, but it still ignores the theme's brightness-dependent color relationships
and makes one mid-tone value satisfy mutually opposed Light and Dark surfaces. It also leaves
future High Contrast handling as another independent exception.

### Reuse only built-in Material roles

Map No status, Todo, Doing, and Done directly to existing neutral, secondary, primary, and
tertiary `ColorScheme` roles.

This guarantees theme ownership but does not provide a truthful completion/success role.
Material's built-in scheme has an error role but no standard success role. Reusing tertiary
for Done would encode visual hierarchy rather than task semantics and would make later theme
changes silently alter status meaning.

### Use one cyan family and distinguish states only by tone

Give all four actions the seed hue at four different tones.

This is maximally harmonious but weakens semantic scanning. Doing and Done benefit from a
controlled hue difference, while No status and Todo should remain neutral. Tone alone also
makes the four adjacent action backgrounds less robust for users with reduced contrast
perception.

### Keep the existing four colors

The current colors already make the actions distinct and the row rails pass the repository's
existing `3:1` surface checks. Keeping them avoids golden changes.

This does not address the visual mismatch shown in the reference, the current Done/white
text contrast shortfall, or the missing Light/Dark foreground pairing.

## Acceptance criteria

- The decision covers only `No status`, `Todo`, `Doing`, and `Done` quick-action colors.
- Normal Light and Dark themes use explicit background/foreground pairs rather than one
  fixed background with universal white foreground content.
- Every action label and icon has at least `4.5:1` contrast against its action background.
- Every status background used as a rail has at least `3:1` contrast against the current
  Light or Dark theme surface.
- Doing remains visually tied to the `#00262F`-seeded Material primary family.
- Done remains semantically distinguishable from Doing without using a high-chroma generic
  green.
- No status remains neutral and does not gain a timeline row rail.
- Labels, icons, semantics, and enablement continue to communicate status without relying on
  color alone.
- Compact and narrow runtime goldens show four distinct adjacent actions without clipping or
  changing the established full-bleed geometry.
- Dark appearance tests verify the brightness-specific foreground/background pairs, and
  High Contrast tests verify reuse of the corresponding normal Light or Dark pairs.
- No non-color interaction, model, mutation, layout, `spec/`, Dune, or `bonsai_flutter`
  behavior changes as part of this decision.

## Risks

- Applying Todo, Doing, and Done colors to their shared row-rail tokens changes persistent
  timeline color as well as the transient swipe pane; limiting the change to swipe actions
  would instead break the current shared semantic-token rule.
- Separate Light and Dark pairs expand the token surface and require brightness to become an
  explicit `Journal_visual_tokens.resolve` input.
- The proposed No status and Todo colors intentionally remain related neutral blue-grays.
  Their label and icon differences are required because hue alone is not a sufficient cue.
- Reusing the normal Light or Dark pair in High Contrast deliberately gives up additional
  status-specific tone separation. The accepted WCAG contrast remains intact, but the custom
  status colors will not increase contrast in step with the generated Material scheme.
- Golden updates could hide unintended geometry changes if color and layout changes are mixed.
  Any implementation should constrain regenerated differences to color pixels.

## Consequences

- Quick status actions now follow Light and Dark appearance changes without changing their
  action order, geometry, labels, icons, semantics, or enablement.
- Dark appearance uses light status backgrounds with explicit dark icon-and-label
  foregrounds instead of retaining universal white foreground content.
- Todo, Doing, and Done row rails change with brightness and continue to match their quick
  action backgrounds.
- High Contrast changes the generated Material scheme around the actions while preserving
  the corresponding normal Light or Dark custom status pair.
- No status remains absent from row rails, and Later and all non-color status behavior remain
  unchanged.
- The exact palette and WCAG thresholds are protected by OCaml application and semantics
  tests plus real-runtime Flutter coverage across all four appearance combinations.
- The macOS application was built and exercised in Light, Dark, and Dark High Contrast
  appearances; the temporary system settings were restored after validation.
