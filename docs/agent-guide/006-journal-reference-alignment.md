# Journal Reference Alignment Implementation Plan

Goal: Close the approved Journal timeline gaps against the supplied mobile reference while preserving the working OCaml ownership, local durability, bounded rendering, and accessibility contracts.

Architecture: The current OCaml and Bonsai application remains the only owner of product state, routes, domain behavior, persistence policy, visual tokens, semantics, and the logical widget tree.
The work is divided into an immediately implementable visual-alignment lane and explicit deferred boundaries, and negative boundary assertions remain in place for Search, date selection, and attachments.

Tech Stack: OCaml 5.1.1, Bonsai v0.17, the pinned public `bonsai_flutter` dependency, DataScript OCaml native SQLite, Flutter 3.44.8, Dart 3.12.2, Swift platform calendar formatting, Dune, and `bonsai_flutter_test`.

Related: Builds on `docs/agent-guide/005-journal-timeline-ui.md`, uses `docs/agent-guide/005-journal-timeline-ui_acceptance_report.md` as the implemented baseline, supersedes only the visual-alignment decisions identified below, and preserves the `005` omission of Search, complete date selection, and attachments.

## Problem statement

The current application is a working local-first Journal timeline rather than a visual prototype.
It already supports durable plain-text entries, optional task state, direct children, Capture, Detail editing, bounded paging, route restoration, recovery behavior, dark and high-contrast palettes, reduced motion, RTL layout, and adaptive known-height rows.

The supplied `941 x 1672` reference image is also the image already analyzed by `005` as the root Journal product authority.
The first release intentionally implemented a reduced milestone and explicitly omitted Search, styled hashtags and mentions, attachment thumbnails, complete Menu and More behavior, and complete date selection.

The remaining mismatch is therefore a mixture of visual defects, accepted omissions, new product scope, framework capability gaps, and incomplete manual evidence.
Treating all of these as CSS-like polish would hide required route, repository, Worker, data-model, platform, and accessibility decisions.

This plan defines the delta from the current working tree.
It does not restore the obsolete Mail-inspired design, the removed Search implementation, any Dart product runtime, any old database path, or any compatibility layer.

## Localized date contract

Canonical journal identity remains the integer `YYYYMMDD` day and the stored page title remains non-authoritative display metadata.
The UI must never use the localized string as a key, cursor, or persistence identity.

The existing application platform request must format the currently visible distinct days under the current calendar generation.
The Swift formatter must use a locale-aware compact weekday, month, and day template equivalent to `EEE, MMM d` in English rather than a hard-coded English format string.

The application must cache formatted labels by calendar generation and day.
A locale or time-zone event must invalidate the visible label cache, issue a new bounded request, and ignore an older response.

The formatted date is view-only in this increment.
It must not expose button semantics, a disclosure chevron, a date-selection route, or a hidden activation handler.

If formatting fails, the UI must show `Date unavailable` for the header and a truthful non-localized safe label for an older heading.
That failure is not permission to persist localized strings or to mutate journal-day identity.
