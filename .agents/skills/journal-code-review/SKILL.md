# Journal Code Review

只读审查请求范围内的代码，只报告问题，不修改代码或其他文件。

先记录审查目标、base/head SHA（未提交修改另记 diff 身份）和文件范围。独立审查应由未实施该变更的审查者执行；只审查委托范围，不运行构建、安装、登录或远端写入。按需读取 [回归与最终验证范围](references/validation.md)，核对结论是否绑定最终源码。后续修改使相关结论失效时，补审受影响范围。

## 性能

- 检查读写放大：单次操作是否重复全量读取、遍历或重写，结合数据量与调用频率判断影响。
- 检查每份持久化数据是否确需跨重启保存、能否从现有权威数据推导或仅驻内存，并评估重复存储的一致性与生命周期清理成本。
- `List` 仅用于明确小于 1000 项的数据，数量未知或可能 >= 1000 时应改用 `rrbvec`（已有依赖时使用 `Rrbvec` 向量），重点检查高频 `List.length`、`List.nth`、`List.append`、`List.concat` 等线性调用及重复拼接造成的 O(n²)。

## UX

- 检查操作进度、结果与失败是否有清晰反馈。
- 逐一检查所有可见按钮，点击必须有对应操作或明确反馈，不可操作时明确禁用并解释原因，不能静默无响应。
- 检查取消、返回与退出是否可达且能安全结束当前操作。
- 检查界面呈现与实际状态是否一致。
- 检查关键操作的可访问性，包括语义标签、焦点顺序与辅助技术支持。

## type

- 检查 `spec/` 下的 `.mli` 类型能否加强约束，以排除非法状态、区分身份与生命周期并限制构造权限。

仅报告有证据的问题，每点尽量一句，包含严重度、位置、触发条件与影响，并标明实证或推断；无发现时明确说明。
